# rubber-workflow

한 덩어리의 작업을 DELTA 단위로 나눠 실행하는 절차. 이 저장소에서 "로드맵"은
`docs/product/roadmap.md`(무엇을 할지, 단계 R0~R9)를 뜻하므로 실행 절차는 "rubber-workflow"라고
부른다. DELTA를 미리 다 계획하지 않고 작업 중 발견에 따라 그때그때 추가·분할하는 탄력성("고무")이
핵심이다.

## 진입 경로

다음 둘 중 하나로 시작한다. 어느 쪽이든 사용자가 실행을 지시하기 전에는 시작하지 않는다.

- **브레인스토밍**: 사용자와 논의해 확정한 작업(브레인스토밍 스킬의 설계 승인 등). 관련 단계가
  없다.
- **로드맵 단계**: `docs/product/roadmap.md`의 단계 하나(예: R1) 또는 그 일부. 로드맵은 함수
  시그니처와 오류 계약을 단계 시작 시 작성하는 design spec에 맡기므로, 그 단계의 design spec이
  승인돼 있어야 한다. 없으면 브레인스토밍으로 spec부터 만든다.

둘 다 아래 절차는 동일하다. 단계에서 시작했으면 "마무리"에서 로드맵 완료 표시 여부도 판단한다.

## 언제 쓰나

한 번에 끝내기엔 크다고 판단되는 작업. 사소한 작업(문서 한 파일 수정, 설정 한 줄 변경)에는
쓰지 않는다 — 그런 작업은 바로 한다.

## 작업공간

`_works/<yyyyMMdd>-NN-<제목>/` (`_works/`는 `.gitignore` 대상). `_works/` 바로 아래에서
`yyyyMMdd-NN-` 접두어가 붙은 폴더만 작업 폴더로 취급하고, 다른 항목은 작업과 무관한 자료이므로
건드리지 않는다. 완료된 작업 폴더는 `_works/_completed/`로 옮긴다(아래 "마무리" 참고) — 진행
중인 작업 폴더만 `_works/` 바로 아래에 있다.

```text
_works/20260920-01-r1-secure-bytes/
  _meta.md               # 작업 브랜치·관련 단계·상태 — 다른 에이전트가 이어받기 위한 최소 정보
  checklist.md            # 목표·범위·DELTA 목록·최종 완료 조건
  DELTA-01.md
  DELTA-02.md
  DELTA-02a.md            # 작업 중 분할/추가된 것
  pending-traps/
    01.md ...
  pending-issues/
    01.md ...
```

## 시작

작업 폴더를 만들고 `_meta.md`, `checklist.md`를 순서대로 작성한 뒤 브랜치를 만든다.

```markdown
---
작업 브랜치: r1-secure-bytes
관련 단계: R1 # 브레인스토밍에서 시작했으면 "없음"
상태: 진행중
---
```

`_meta.md`는 이 세 필드만 가진다. **진행 로그를 쓰지 않는다** — 판단이 필요했던 지점은
해당 `DELTA-NN.md`의 "## 결정" 절에 남긴다(아래 "DELTA-NN.md 형식" 참고). 상태는 `진행중`
/ `완료` 둘 뿐이고, 다른 에이전트가 이 작업 폴더를 이어받아도 되는지 판정하는 용도로만
쓴다.

`_meta.md` 작성 후 `git switch -c <작업 브랜치> dev`로 브랜치를 만든다.

## checklist.md

작업 시작 시 작성.

```markdown
# <제목> 완료 체크리스트

- 목표: ...
- 범위(포함/제외): ...
- 관련 단계: R1 (브레인스토밍에서 시작했으면 생략)

## DELTA 목록

- [ ] DELTA-01: <한 줄 스코프>
- [ ] DELTA-02: <한 줄 스코프>

## 완료 조건

- [ ] 조건 1
- [ ] 조건 2
```

로드맵 단계에서 시작했으면 완료 조건에 그 단계의 완료 조건을 옮겨 적는다(작업이 단계의 일부면
해당하는 항목만).

DELTA 목록은 **확정이 아니다** — 작업 중 언제든 추가·분할한다. 빠진 게 발견되면 바로
목록에 한 줄 추가하고 계속 진행한다(별도 승인 없이). 기존 DELTA를 쪼개야 하면
`DELTA-01a`, `DELTA-01b` 형태로 추가한다(뒤 번호를 밀지 않음).

## DELTA-NN.md 형식

```markdown
# DELTA-NN <한 줄 제목>

## 계획

- 목적:
- 변경 대상:
- 완료 기준(검증 방법 포함):

## 결과

<!-- 비어 있으면 이 DELTA는 아직 진행 중(또는 미시작)이라는 뜻 -->

- 상태:
- 검증 근거:
- 발견/처리:
- 남은 위험:

## 결정

<!-- 판단이 필요했던 지점만, 있을 때만 추가. append-only -->
```

"## 결정"은 이 DELTA를 진행하며 애매한 것을 임의로 골라야 했던 지점을 남긴다 — 주제,
결정, 근거, 틀렸을 때 비용을 적는다. 없으면 절 자체를 생략한다.

## DELTA 사이클

DELTA 하나 = 계획 → 구현 → 확인 → 정리, 한 번에 끝까지.

1. checklist의 DELTA 목록에서 다음 하나를 고른다(번호 순서 고정 아님).
2. `DELTA-NN.md`를 만들고 "## 계획"에 목적·변경 대상·완료 기준(검증 방법 포함)을 적는다.
3. 구현한다. 테스트 가능한 부분은 실패(RED) 확인 후 최소 구현으로 통과(GREEN).
4. 완료 기준을 실제로 확인한다(`pnpm check-types`, `pnpm lint`, `pnpm build`, 범위에 해당하는
   테스트·게이트 명령의 실행 결과 등 — 근거를 남긴다).
5. `DELTA-NN.md`의 "## 결과"에 상태·검증 근거·발견한 것·남은 위험을 적는다.
6. 함정/후속 작업을 발견하면 `pending-traps/`, `pending-issues/`에 바로 적어둔다 — 승격
   판단은 지금 하지 않는다.
7. checklist의 DELTA 체크박스와 완료 조건을 갱신한다.
8. 작업 브랜치에 커밋한다(아래 "브랜치와 병합" — 자유롭게, 매번 확인받지 않음).
9. 다음 DELTA를 고른다. 목록이 비면 완료 조건을 재확인하고, 다 채웠으면 마무리한다.

## 이어받기 (다른 에이전트가 이어서 진행)

새 에이전트는 대화 맥락 없이 작업 폴더 경로만 받을 수 있다. 다음 순서로 상태를 복원한다.

1. `_meta.md`를 읽는다. `상태: 완료`면 더 할 일이 없다 — 사용자에게 보고하고 멈춘다.
2. `git switch <작업 브랜치>`로 전환한다. 브랜치가 없으면 사용자에게 보고하고 멈춘다 —
   추측해서 새로 만들지 않는다.
3. `checklist.md`를 읽어 목표·범위·완료 조건·DELTA 목록(체크 상태)을 파악한다.
4. 존재하는 `DELTA-NN.md`를 번호 순으로 읽는다. "## 결과"가 채워져 있으면 그 DELTA는
   완료된 것이다. **마지막 파일의 "## 결과"가 비어 있거나 그 DELTA 파일 자체가 아직
   없으면, 그 DELTA가 진행 중(또는 미시작)이라는 뜻** — 이어서 그 DELTA부터 계속한다.
5. 각 `DELTA-NN.md`의 "## 결정"(있으면)을 읽어 이미 내린 판단과 근거를 파악한다. 같은
   판단을 다시 하지 않는다.
6. `pending-traps/`, `pending-issues/`에 이미 있는 임시 기록은 그대로 두고 이어서
   추가한다 — 마무리 시점 전까지 승격 여부를 판단하지 않는다.

무엇이 없거나 애매하면(브랜치가 없다, `_meta.md`가 없다, 마지막 DELTA 파일에 계획과 결과
둘 다 비어 있다 등) 추측해서 진행하지 않고 사용자에게 보고한다.

## 브랜치와 병합

- 작업 브랜치는 항상 `dev`에서 분기한다.
- 브랜치 이름은 작업 폴더의 `<제목>`(날짜 접두어 제외). 예: `r1-secure-bytes`.
- DELTA 진행 중에는 이 브랜치에 필요한 만큼 자유롭게 커밋한다 — `main`이 아니라 작업
  브랜치이므로 매 커밋 확인은 받지 않는다.
- checklist를 다 채우면 `dev`로 병합하기 전에 커밋을 의미 단위로 재그룹화해 커밋 수를
  줄인다(아래 "재그룹화"). 병합은 `dev`에 `git merge --ff-only`로만 한다.
- `main`으로의 병합·rebase·push는 하지 않는다. `main` 작업은 사용자가 별도로 지시한다.
- 작업 브랜치는 원격에 push하지 않는다. 재그룹화가 히스토리를 다시 쓰는데 force push는
  금지이기 때문이다. `dev`의 push는 사용자가 지시할 때만 한다(원격이 공개 저장소).
- 작업 브랜치의 커밋 해시는 재그룹화로 바뀔 수 있다 — `dev`로 병합되기 전까지 checklist·
  DELTA 문서·이슈 초안에 해시를 적지 않는다. 참조는 파일 경로·테스트 이름으로 하고, DELTA
  번호는 작업 폴더 안의 문서에서만 쓴다.

### 재그룹화

`git rebase -i`는 쓰지 않는다 — 에이전트 세션은 `GIT_EDITOR`가 비대화형이라 아무것도
합치지 않은 채 "Successfully rebased"를 반환할 수 있다(`GIT_SEQUENCE_EDITOR` 우회도
마찬가지). 대신:

1. 백업 ref를 남긴다: `git update-ref refs/backup/<브랜치>-pre-squash HEAD`
2. `git log --oneline --name-only dev..HEAD`로 의미 단위 그룹을 정한다.
3. `git switch --detach dev` 후 그룹별로 `git cherry-pick -n <커밋...>`과
   `git commit -m "..."`을 반복한다.
4. `git diff refs/backup/<브랜치>-pre-squash HEAD --stat`로 트리가 같은지 대조한다(의도적
   으로 버린 커밋이 없다면 빈 출력).
5. `git branch -f <브랜치> HEAD` 후 `git switch dev && git merge --ff-only <브랜치>`.
6. 병합 후 백업 ref를 지운다: `git update-ref -d refs/backup/<브랜치>-pre-squash`
7. 작업 브랜치를 삭제한다: `git branch -d <브랜치>`

커밋 메시지는 한글, 컨벤셔널 커밋(`feat:`/`fix:`/`refactor:`/`style:`/`docs:`/`test:`/`chore:`
등)으로 쓰고, `claude`, `Generated with`, `Co-Authored-By`, `Claude-Session` 문구를 넣지 않는다.

## 마무리

checklist의 완료 조건을 전부 만족하면:

1. `pending-traps/`, `pending-issues/`를 훑어 승격 여부를 판단한다(아래 기준).
2. 로드맵 단계에서 시작한 작업이면 로드맵 완료 표시 여부를 판단한다. 그 단계의 완료 조건과
   로드맵의 "릴리스 판정" 조건을 전부 만족했을 때만 완료로 본다. 일부만 끝났으면 로드맵을 바꾸지
   않는다. 완료로 판정하면 단계 제목 아래에 `**상태:** 완료 (YYYY-MM-DD)` 한 줄을 추가하고,
   "알려진 제한"과 "다음 단계 범위"를 `CHANGELOG.md`의 `Unreleased` 절에 그 단계 항목으로
   기록한다(로드맵 "릴리스 판정"). 브레인스토밍에서 시작한 작업이면 이 단계는 없다.
3. "브랜치와 병합"에 따라 재그룹화 후 `dev`에 병합한다.
4. `_meta.md`의 `상태`를 `완료`로 바꾼다.
5. 작업 폴더를 `_works/_completed/<원래 폴더명>/`으로 옮긴다(`mv`, 이름은 그대로 —
   이미 `yyyyMMdd-NN-<제목>` 형식이라 재명명하지 않는다). `_works/`가 통째로 gitignore
   대상이라 이 이동은 git에 기록되지 않는다.

### 함정 → 장기 문서화

모두 만족해야 승격: (1) 다시 겪을 조건을 특정할 수 있다 (2) 성공한 것처럼 보이는 신호가
있어 조용히 넘어갈 위험이 있다 (3) 재발 가능성이 있다.

승격하면 `docs/traps/`에 `INDEX.md` + `TRP-NNN-<slug>.md`(3자리, 001부터, 삭제한 ID 재사용
안 함) 형식으로 기록한다. 처음 승격할 때 디렉터리와 `INDEX.md`를 만든다. 승격 문서는 추적
문서이므로 `_works/` 경로와 DELTA 번호를 적지 않는다.

```markdown
# TRP-NNN <제목>

- 상태: ACTIVE
- 적용 조건: <무엇을 할 때 해당하는지>

## 오해하기 쉬운 신호

## 원인

## 탐지/회피
```

승격하지 않으면 그 작업 폴더의 `pending-traps/`에만 남고 자연 소멸한다.

### 후속 작업 → 등록

- 제품 범위를 넓히는 후속(새 기능·옵션)은 로드맵의 "기능 추가 판정 기준" 셋에 모두 "예"여야
  한다. 로드맵 수정은 사용자 승인 후에 한다.
- 그 밖의 후속(버그, 테스트 보강, 문서, 리팩토링)은 GitHub Issue로 등록한다
  (`docs/agents/issue-tracker.md`). 원격이 공개 저장소이므로 제목·본문 초안을 사용자에게
  보여 승인받은 뒤 `gh issue create`를 실행한다. 본문에 `_works/` 경로, DELTA 번호,
  재그룹화 전 커밋 해시를 적지 않는다.
- 등록 여부는 매번 판단한다 — 사소하면 버려도 된다.

## 금지

- `git rebase -i`, `GIT_SEQUENCE_EDITOR` 우회
- 재그룹화 없이 `dev`에 병합(커밋이 그대로 늘어나는 것 방지)
- `main`을 대상으로 하는 merge, rebase, push
- 작업 브랜치 push
- `git reset --hard`, force push, 광범위한 `git clean`
- 사용자 승인 없는 `gh issue create`
